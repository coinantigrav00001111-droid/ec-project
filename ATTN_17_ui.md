## 17.0. Концепт и границы

Сейчас UI вырос из трёх копий «панель категорий + панель объектов» (Build, Operate, Observe) и одной InfoPanel на 779 строк. Нужно привести его к архитектуре, в которую можно добавлять верхнюю панель со статистикой, меню, окно настроек, боковую панель, отладочную панель и перетаскиваемые окна, не копируя код в четвёртый раз.

**Порядок работы (решено):** сначала рефакторинг без изменения внешнего вида, потом новые элементы.

| Фаза | Что делаем | Шаги |
|---|---|---|
| A. Рефакторинг | дефекты, настройки, развязка с игрой, один каталог кнопок, InfoPanel по вкладкам, хоткеи, локализация | U0–U7 |
| B. Каркас и новое | HUD-слоты, TopBar со статистикой, меню, окно настроек, боковая панель, перетаскиваемая InfoPanel, DebugPanel, повтор последнего, DC в Operate | U8–U16 |
| C. Внешний вид | токены темы, иконки, анимации, тултипы и тексты, метки в мире | U17–U20a |
| D. После | экраны и роутер, выбор рамкой, инструменты-сущности, затем масштаб интерфейса, F1-справка, Library, 3D-контроллер | U21–U23, roadmap |

**Вне объёма:** масштабирование интерфейса, полная справка по клавишам (F1), пауза, снимок, индикатор сохранения, часы, содержимое Library, 3D-версия DC-контроллера. Под них оставляем место в раскладке (§17.4), но не строим.

**Целевое разрешение [решено]:** HD = 1920×1080. Рабочее разрешение разработки и база дизайна 1600×900, проверка на 1920×1080. Окно проекта уже 1600×900, режим растяжения не задан (задаём в U8). 1280×720 в требования не входит.

### 17.1.4. Что в архитектуре уже хорошо (не ломаем)

- Правило проекта «сигналы вверх, вызовы вниз» (см. заголовок `ui_generator.gd`) верное, нужно только провести его через границу UI и игры.
- `Hints` как автолоад с контекстами, а не текстами в источниках: образец для остальных сервисов.
- Данные карточек Observe одной константой, ресурсы `EntitySetting` для объектов: каталог уже data-driven.
- Динамические вкладки InfoPanel по компонентам (Mechanisms, Terrain), построенные кодом.
- Один файл темы `theme_gray.tres` и `theme_type_variation` (`ModeButton`, `ObjectButton`, `TagButton`, `HeaderSmall`).

## 17.3. Целевая архитектура

### 17.3.1. Дерево

```
UI (CanvasLayer, layer 0)
├── Services (Node)
│   ├── ModeController          режим, владелец Global.current_mode, реестр режимов
│   ├── ToolbarController       один на все режимы: категории → теги → кнопки
│   └── UIPointer               «курсор над UI?», стек Esc
├── HUD (Control, полный экран, mouse_filter = IGNORE)
│   ├── TopBar                  PanelContainer, на всю ширину, высота 40
│   │   ├── Left:   SystemMenuButton, LayoutNameLabel
│   │   ├── Center: StatsBar (StatChip × N, расширяется)
│   │   └── Right:  ModePanel
│   ├── ToolDock                левый нижний угол: CategoryBar, ActionsStrip, TagColumn, ItemGrid
│   ├── SideDock                выдвижная боковая панель (QoL), справа
│   ├── Floating (Control)      FloatingPanel: InfoPanel, DCPanelHost, DebugPanel
│   └── HintSlot                место под подсказки (сам Hints остаётся автолоадом)
├── Windows (CanvasLayer, layer 20)
│   ├── SettingsWindow
│   └── ConfirmDialog, SaveLoadDialog
└── Toasts (CanvasLayer, layer 30)
```

Статистику макета (`LayoutStats`) считает игровая модель в `core/layout_stats.gd`, а не UI. Так нет цикла «UI сканирует дерево».

### 17.3.2. Кто чем владеет

| Объект | Владелец | Знает про игру | Знает про UI |
|---|---|---|---|
| выбранная сущность | `ToolController` (сигнал `selection_changed`) | да | нет |
| режим | `ModeController` (сигнал `current_mode_changed`, пишет `Global.current_mode`) | нет | да |
| инструмент | `ToolController` (сигнал `tool_changed`) | да | нет |
| статистика макета | `LayoutStats` (сигнал `changed`) | да | нет |
| настройки на диске | `Settings` | нет | нет |
| положение окон | `Settings` (секция `[ui]`), пишет `FloatingPanel` | нет | да |
| опции строительства (шаг поворота, снап, сетка, лимиты) | `BuildOptions` (ресурс в `Global`) | да | нет |
| клавиши | `InputMap` | да | нет |
| тексты | `Translation` (`tr()`) | нет | нет |

### 17.3.3. Каталог кнопок

Одна механика вместо трёх копий.

```gdscript
class_name CatalogProvider extends RefCounted
signal changed
func get_categories() -> Array[Dictionary]      # {id, title_key, icon}
func get_tags(cat: StringName) -> Array[Dictionary]   # пусто: тегов нет (Observe)
func get_items(cat: StringName, tag: StringName) -> Array[Dictionary]
# item: {id, title_key, icon, tip_key?, group?, toggle?, locked?, payload}
```

| Режим | Провайдер | Кто принимает нажатие |
|---|---|---|
| Build | `EntityCatalogProvider` (ресурсы `EntitySetting`) | `ToolController._on_build_selected` |
| Operate | `EntityCatalogProvider` + `DCCatalogProvider` | `DCPanelHost` или `ToolController` (для 3D) |
| Observe | `CardCatalogProvider` (константа `CARDS`) | `ObserveController.observe_action` |
| Library | `LibraryProvider` (пока пустой, показывает «скоро») | — |

`ToolbarController` один, состояние (последняя категория, тег) хранит по режимам. `CatalogButton` одна сцена, вид задаётся `theme_type_variation` (`ModeButton`, `TagButton`, `ObjectButton`, `Card`). Режим меняет только провайдера и приёмника. Новая категория добавляется в провайдере, без правки сцены и контроллера.

### 17.3.4. Базовые виджеты

| Виджет | Назначение | Где нужен |
|---|---|---|
| `FloatingPanel` | заголовок, перетаскивание, сворачивание, изменение размера, запоминание положения, прижим к экрану | InfoPanel, DC, DebugPanel |
| `SlidePanel` | панель от края экрана, язычок, анимация, закрепление | SideDock |
| `StatChip` | иконка, значение, тултип, скрытие нуля | TopBar |
| `ModalWindow` | затемнение, заголовок, Esc закрывает | Settings, диалоги |
| `ToggleRow`, `SpinRow`, `OptionRow` | строка настройки: подпись + элемент + сброс | Settings, SideDock, DebugPanel |
| `Toast` | короткое сообщение, исчезает само | отказы строительства, сохранение |

### 17.3.5. Правила

- Сигналы вверх, вызовы вниз. Игровой код не получает ссылок на UI, UI подписывается на сигналы игры.
- Узлы находятся через `@export var x: Node` или группы, не строкой `'%' + name`.
- Ни одного абсолютного `offset_*` у HUD-элементов: только якоря, контейнеры и `custom_minimum_size`.
- Каждая панель: `mouse_filter = STOP` на самой панели и `IGNORE` на прозрачных обёртках. Инструменты работают через `_unhandled_input`, поэтому клик по панели до них не доходит. Hover-луч дополнительно спрашивает `UIPointer.is_over_ui()`.
- Любая строка для игрока идёт через `tr(key)`. Строки для отладки не переводятся (помечаются `# no-loc`).
- Размеры, цвета, отступы из темы, не из скриптов (§17.6).

## 17.5. Локализация

### 17.5.1. Требования

- Языки на старте: ru и en. Остальные добавляются колонкой в CSV без правок кода. Fallback: en.
- Смена языка на лету из окна настроек, без перезапуска.
- В коде и сценах нет текстов для игрока, только ключи.
- Макет переживает удлинение текста на 30–40% (русский и немецкий длиннее английского): нет абсолютных ширин под текст, у длинных подписей `autowrap` или `text_overrun_behavior`.
- Данные сохранений не зависят от языка: в сейве id и пути ресурсов, не названия.

### 17.5.2. Архитектура

| Что | Как |
|---|---|
| Хранилище | `locales/ui.csv` (UI, меню, подсказки, настройки, карточки), `locales/content.csv` (названия и описания объектов). Столбцы: `keys,en,ru` |
| Ключи | латиница, `область.раздел.элемент`: `ui.mode.build`, `hint.build.place`, `obj.track_straight_a.name`, `stats.tracks` |
| Код | `tr("ui.mode.build")`; подстановка через `tr("stats.length") % value`; множественное число `tr_n`; контекст вторым аргументом, если одно слово значит разное |
| Сцены | `Label.text` с ключом переводится автоматически (`auto_translate_mode`). Для текста, собранного кодом, ключ хранится, перевод берётся в момент показа |
| Смена языка | `Settings.ui.language` → `TranslationServer.set_locale`. Динамические элементы (Hints, подписи вкладок, карточки) слушают `NOTIFICATION_TRANSLATION_CHANGED` и перестраиваются. Переведённые строки в переменных не кэшируются |
| Первый запуск | язык ОС, если это ru или en, иначе en |
| Шрифт | `Play` покрывает латиницу и кириллицу. Под другие письменности позже добавляется fallback-шрифт в `FontVariation` |
| Контент | `EntitySetting` получает необязательное поле `name_key` и `desc_key`. Если ключа нет, показывается старое `name`, поэтому переход идёт по одному объекту |
| Единицы | подписи единиц (`u/sm`) тоже ключи. Формат десятичных знаков по локали: на потом |

### 17.5.3. Процесс

- **Псевдолокализация.** В настройках проекта Godot есть режим псевдолокализации: удлиняет и «акцентует» все переведённые строки. Включаем на время проверки: непереведённые строки видны сразу, переполнение макета видно сразу.
- **Линтер ключей.** `tests/loc_lint.gd` (EditorScript, запуск из редактора): находит `tr("...")`, которых нет в CSV, и ключи в CSV, не используемые в коде, и строки с кириллицей в `Label.text` сцен.
- **Объём.** По `grep` в `ui/` и `core/` около 210 строковых литералов с кириллицей в `.gd` и около 130 в `.tscn` и `.tres` (`ui/`, `data/`). Часть из них комментарии в кавычках и отладка, реальных строк для игрока примерно 150–250. Переводим только то, что игрок видит в релизе.
- **Правило для новых строк.** В шагах U0–U6 новые тексты остаются русскими и помечаются `# TODO loc`, чтобы U7 их нашёл. С U7 в код попадают только ключи.

### 17.5.4. Что нужно сделать в редакторе один раз

Godot импортирует CSV сам при открытии проекта и создаёт `ui.en.translation` и `ui.ru.translation` (то же для `content`). Их нужно добавить в Project Settings → Localization → Translations. Это единственное действие руками, остальное в патче (проверка в U7).

### 17.12.1. ID объектов

**Сейчас.** `EntitySetting.id: int` (в коде стоит `#TODO а если id строковый сделать?`). Назначается руками в каждом `.tres`. Проверка на дубль есть, но слабая: `UIGenerator._build_data` пишет `push_error("Duplicate ID")` и молча пропускает второй объект. Используется для сортировки в панели и как подпись на кнопке. Сейвы от id не зависят: хранится `setting_path`.

**Решение [решено]** (принято разработчиком, шаг выполнен в U3a). Не зашифровывать признаки в цифры id. Цифровой код нечитаем, не расширяется (новый признак ломает схему) и дублирует то, что лучше хранить явно. Вместо этого три разные вещи:

| Поле | Что это | Пример |
|---|---|---|
| `key: StringName` | стабильный уникальный ключ, читаемый человеком. Основа для ключей локализации (`obj.<key>.name`, U7), статистики, будущих ссылок в кампании | `track.straight.wood_ballast` |
| `facets: Dictionary` | признаки для фильтров и выбора рамкой | `{shape: straight, ballast: true, sleeper: wood}` |
| `sort_order: int` | порядок кнопок | `110` |

Старый `id: int` остаётся читаемым до миграции всех `.tres`. Аудит 02.11.2026: сейвы от `id` не зависели никогда (хранится `setting_path`), условие «после миграции сейвов» пустое (§17.14.5). **[решено, §17.13 C14]:** `id` удаляется в U3d. Проверка дублей: при загрузке и `tests/catalog_lint.gd`. Если хочется «id с информацией», то это `key` с точечной структурой `категория.тег.вариант`: он читаем, но решения принимаются по `facets`, а не разбором строки. **В плане:** U3a (выполнено, §17.7).

### 17.12.2. Фильтры рядом с тегами

**Сейчас.** Теги (`straight`, `curve`) единственная ось. Вариант оформления (балласт, шпалы) был бы отдельным тегом на каждое сочетание, что даёт комбинаторный взрыв.

**Решение [решено].** Теги остаются основной осью «что это». Фильтры это независимые оси «какое»: балласт (любой, с, без), шпалы (любые, дерево, бетон), позже материал, масштаб. Данные берутся из `facets` объектов (§17.12.1), набор фильтров категории задаётся в `CatalogMeta.facet_specs`. Те же фасеты использует выбор рамкой (§17.12.5). Ответ на вопрос «упростит ли ID»: структурированный `key` помогает группировать, но фильтры строятся только по `facets`. **В плане:** U3a (данные), U3b (интерфейс). Связка с глобальным стилем траков из ATTN_15 не нужна **[решено]**: фильтр лишь отбирает кнопки, стиль меняет вид построенного. **[устарело для траков, §17.13]:** у траков фасетов стиля и фильтров по ним не будет, стиль это настройка сессии, а не признак кнопки; фильтры остаются для других категорий и Library.

### 17.12.3. Полный цикл экранов

Каркас потока (детали в [ATTN_19_game_flow.md](ATTN_19_game_flow.md)):

```
Запуск → Заставка/загрузка → Главное меню
  ├─ Продолжить / Загрузить
  ├─ Новая игра
  │    ├─ Песочница → настройка макета (комната, стол) → Игра
  │    └─ Кампания  → выбор главы → брифинг → Игра → итоги → следующая / в меню

  ├─ Настройки                 окно поверх любого экрана (U11)
  └─ Выход
Игра (Build, Operate, Observe) ←→ Пауза (продолжить, сохранить, загрузить, настройки, в меню, выход)
```

Что уже есть: главная сцена `GameRoot` (запуск сразу в игру), Icon Studio (ATTN_18) как прототип Model Studio, режим быстрой загрузки `--fast`. ### 17.13.2. Модель

```
Категория (Tracks)
 └─ Тег (Прямые, Радиусные, Стрелки и кроссы, Прочие)
     └─ Кнопка формы (R1 36 · 30°)  ──нажатие──►  объект «форма × активный стиль»

Набор стилей проекта (TrackStyleSet): wood, wood_ballast, concrete, concrete_ballast, budget, ...
Активный стиль сессии (TSM.current)  ◄── переключатель стиля (место: U7a)
```

Состояние в игре:

- каталог знает формы и теги и ничего не знает про стили;
- `TSM` (`TrackStyleManager`, ATTN_15 §5.3) держит набор стилей и активный стиль, шлёт `current_changed`;
- форма (`.tres`) оставляет поле `style` пустым: пусто означает «следовать сессии», непустое «зафиксирован» (ATTN_15 §8 п. 6, теперь **[решено]**);
- `EntityFactory.create_from_setting` берёт активный стиль, записывает `style_id` в сущность, визуал строится в этом стиле; призрак строится тем же путём;
- сейв пишет `style_id` у каждого трака, загрузка передаёт его в фабрику (стиль известен до `add_child`).

### 17.13.5. Проблемы, которые видны сейчас

| № | Проблема | Мера |
|---|---|---|
| P1 | **Стыки при смене стиля сессии.** Рельсы с балластом (0.85) и без (0.45) на разной высоте: по проверке 27.10.2026 трак с балластом не примагничивается к траку без балласта, а электрическая связь через ступеньку не создаётся (`joint_level_tol`). ### 17.14.5. Числовой `id` в паспорте сущности

Паспорт объекта это `C_Identity` с ссылкой на `EntitySetting`. На вкладке «Общее» поля `id` нет (там категория, тег, название, описание, иконка, имя узла). Надпись «ID:» на вкладке «Питание» это номер контура клипсы (`ClipContourIDButton`), к паспорту не относится.

Кто читает `EntitySetting.id` сегодня:

| Потребитель | Что делает с `id` | Блокирует удаление |
|---|---|---|
| игровая логика, сейвы (`save_manager.gd:155`: `setting_path`; в U3c добавится `style_id`), порядок кнопок (`sort_order`, имя файла), кнопка объекта (показывает `key`) | не читают | нет |
| Icon Studio (`icon_studio.gd:793`, `:884`) | сортировка списка и подпись | да, мелко; в C14 не упомянут, правится в U3d |
| Track Studio (`test_object.gd`, `track_studio.gd:715`, `tests/track_lib_test.gd`) | выдаёт новый `id`, правит регулярками, проверяет в тесте | да, но снимается в U3d: `test_object.gd` удаляется |
| `ObjectButton` (`object_button.gd:37`) | ветка `str(_obj.id)` для не-`EntitySetting` | нет, это `DCControllerSetting.id` (другой ресурс, C14 его оставляет) |
| 63 `.tres` (39 из них траки) | хранят `id = N` | нет, чистятся в U3d |
| документы (ATTN_12 таблица, ATTN_13 «пресеты 6001…6030», 12 упоминаний) | называют объекты по числу | нет, замена на ключи |

**Когда можно убирать.** Решено в C14: в U3d, вместе с перепиской базы траков; аудит с этим согласен. Момент выбран верно: сейвы `id` не хранили никогда (условие из старого комментария «когда сейвы перейдут» пустое), а главный потребитель, Track Studio, удаляется в том же шаге. **Поправка к C14:** формулировка «в логике не используется, только подпись в debug» неточна, `id` ещё читает Icon Studio (сортировка и подпись). Без правки `icon_studio.gd` студия сломается на удалённом поле; поэтому в U3d добавлен пункт со списком (Icon Studio, явный `key` у `foam_polygon` и `foam_strip`, правило в `catalog_lint`, документы). Подготовительное правило можно ввести уже сейчас: новые `.tres` пишутся без `id`. Поле `key` остаётся навсегда, оно основа локализации (U7) и ссылок кампании.

**Оговорка.** Единственное место, где нужен стабильный идентификатор, формат сейва: он ссылается на путь ресурса (`setting_path`), переименование файла объекта его ломает. §17.13 (P5) уже предусматривает `form_id` в сейве для таблицы форм (U3g); перевод сейва на `key` в план не вошёл, записывается в roadmap (§17.9) отдельным пунктом.
