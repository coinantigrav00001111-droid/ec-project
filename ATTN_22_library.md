## 22.0. Концепт и границы

**Library это режим игрока**, мастерская и коллекция моделей. Игрок открывает готовую модель, рассматривает её и читает справку о прототипе, красит, меняет детали, ставит свет и механизмы, проверяет и подстраивает, собирает здание «из литников» или строит своё. Результат попадает в каталог Build и на макет.

Три слоя режима:

| Слой | Что даёт игроку | Подраздел |
|---|---|---|
| Collection | витрина, осмотр, справка по реальному прототипу, открытие моделей | §22.7.1 |
| Workshop | покраска, детали, свет и механизмы, стенд (тест и подстройка), реставрация | §22.7.2 – §22.7.4 |
| Builder | сборка из литников и генерация зданий | §22.7.5, §22.7.6 |

**Icon Studio и Track Studio остаются инструментами автора контента** ([ATTN_20](ATTN_20_track_studio.md) §20.1: «не часть игры и не для игрока»). Они не превращаются в экраны игрока. Library берёт у них код: мир с объектом, камеру, Fit, слоты ракурсов, окно и файл настроек, сборщик материалов, схему «список, рабочая копия, проверка, запись».

**Название [предложение].** «Library» это название режима и кнопки на `ModePanel` (то, что видит игрок). «Model Studio» это название рабочего экрана мастерской внутри режима. Код остаётся в `core/library/`, идентификатор режима `&'library'` не меняется (он зашит в `Global.current_mode`, `ModeController`, `Hints`). Закрывает три открытых вопроса о названии (ATTN_17 §17.12.12 п. 3, ATTN_18 §18.7 п. 7, ATTN_19 §19.11 п. 5); сами документы правятся после согласования (§22.13).

**В объёме:** всё перечисленное в таблице слоёв; правила режимов игры и сложности (§22.4); рабочий экран и выход из него (§22.5); данные игрока (коллекция, исполнения); план интерфейса; шаги L0–L12 с проверками в редакторе.

**Вне объёма:** содержание кампании (главы, цели, награды: [ATTN_19](ATTN_19_game_flow.md) §19.9); система повреждений в игре (GDD §10 «Мастерская повреждений»: Library получает только заготовку, §22.7.4); звук (TDD roadmap п. 6, у Library только слот); импорт чужих моделей игроком; онлайн и обмен блюпринтами (формат данных готов к нему, §22.6.2).

## 22.3. Принципы

1. **Один объект, один путь [предложение].** Любое действие Library применяется к `EntitySetting` и данным исполнения (`ModelVariant`). Нового типа сущности «модель коллекции» нет.
2. **Данные, не ветвление кода [предложение].** Исполнение, паспорт, набор это данные; код читает их, а не знает про конкретные модели.
3. **Ядро без интерфейса [решено в ATTN_20 §20.2, переносится].** Всё, что можно вызвать без окна (применение исполнения, раскладка литника, сборка здания, проверки), лежит без `Control` и тестируется сценами `tests/library_*`.
4. **Тот же код, что в игре [решено в ATTN_18 §18.2, переносится].** Объект в студийной сцене создаёт `EntityFactory`; свет и фон студийные, `GFX` игры не используется.
5. **Без наказания [решено, GDD §2].** Нет таймеров, штрафов и необратимых действий; любой шаг можно отменить или сбросить.
6. **Каждая опция имеет флаг [предложение].** Интерфейс спрашивает `LibraryRules`, а не режим игры (§22.4).
7. **Контент автора в `res://`, данные игрока в `user://` [предложение].** Запись в `res://` работает только из редактора ([ATTN_20](ATTN_20_track_studio.md) §20.1); игрок пишет в `user://` и только JSON (F7).
8. **Старое не ломается [предложение].** Сейв без поля исполнения, модель без паспорта и без разметки деталей работают как раньше.

## 22.4. Режимы игры, сложность и отключение опций

**[=атн=] «Учесть отключение определённых опций для режимов игры песочница\прохождение кампании\уровень сложности».** Устройство то же, что у электрики ([ATTN_10](ATTN_10_dc_power_system.md) §10.5.11): сложность это выбор пресета плюс отдельные тумблеры. Пресеты Library соответствуют точности электрики: Простая это P0, Стандарт P1, Реалистичная P2.

**`LibraryRules`** (ресурс, код без интерфейса) **[предложение]**. Интерфейс не знает про «песочницу» и «кампанию», он спрашивает ключ: `rules.level(&"paint")`, `rules.allows(&"parts.swap")`.

| Ключ | Тип | Значения |
|---|---|---|
| `source` | enum | `SANDBOX`, `CAMPAIGN` |
| `preset` | enum | `SIMPLE`, `STANDARD`, `REALISTIC` |

| `paint.level` | 0–3 | 0 нет; 1 цвет зон; 2 плюс отделка; 3 плюс декали и износ |

| `restore.enabled` | bool | реставрация |
| `debug.all` | bool | открыть всё (только debug) |

Стартовые значения **[предложение]**:

| Опция | Песочница, Простая | Песочница, Стандарт | Песочница, Реалистичная | Кампания |
|---|---|---|---|---|
| Коллекция | открыта | открыта | открыта | открывается опытом и главами |
| Справка о прототипе | да | да | да | да |
| Покраска | 1 | 2 | 3 | по главе |

| Тест | кнопка (0) | стенд (1) | подстройка (2) | по главе |
| Сборка | пропуск (0) | упрощённая (1) | полная (2) | по главе, как награда-ритуал |
| Генератор | готовые (0) | модули (1) | плюс прототип (2) | по главе |
| Реставрация | нет | по желанию | по желанию | задания |

**Где хранятся.** Правила лежат в сейве макета (как `ControlMode`, ATTN_16 D10, и `DCSRules`, ATTN_10) и в профиле как значение по умолчанию для Library, открытой без макета. Выбираются в `sandbox_setup` ([ATTN_19](ATTN_19_game_flow.md)); до него пресет переключается в отладочной кнопке шапки Library. Кампания переопределяет правила главы (`Chapter`, ATTN_19 §19.9). Когда появятся `DCSRules` и `ControlMode`, `LibraryRules` становится секцией общих правил игры (Q7).

**Как выглядит отключённая опция [открыто, Q8].** Предложение: серая с причиной («Доступно в режиме Стандарт»), кроме Простой, где такие опции скрываются, чтобы не загромождать экран.

**Открытие моделей.** Источники: опыт (XP) за действия в Library и награды глав. Денег нет. XP лежит в профиле. Проигрыша нет: закрытая модель остаётся серым силуэтом с условием открытия.

## 22.5. Рабочий (переходный) экран

**[=атн=] «Нужно предложение: рабочий (переходный) экран режима. Выход из него в отдельную сцену\экран в зависимости от типа студии или работа в одном».**

### 22.5.1. Предложение: один экран, сменные рабочие области

Экран `library` (в ATTN_19 числится как `studio`, Q2) это одно окно с одним 3D-миром (`StudioWorld` в `SubViewport`) и сменными рабочими областями (`Workspace`): Осмотр, Покраска, Детали, Свет, Стенд, Реставрация, Сборка, Здания. Выбранный объект, камера и исполнение общие, поэтому переходы мгновенны, а «применить исполнение» написано один раз.

```
game (кнопка Library на ModePanel)
  └─→ library  (оверлей поверх игры, мир игры на паузе)
        ├─ Осмотр ........... тот же экран, сцена Clean / Витрина
        ├─ Покраска, Детали, Свет, Стенд, Реставрация ... тот же экран, сцена Clean / Стол
        ├─ Сборка ........... тот же экран, своя рабочая область (стол с литниками)
        ├─ Здания ........... тот же экран, своя рабочая область (плита-основание)
        └─ Студии автора .... ОТДЕЛЬНЫЕ сцены: Icon Studio, Track Studio (только debug)
  ←─ «Назад» / Esc: возврат в игру, в прежний режим HUD
```

**Правило выбора «отдельная сцена или один экран» [предложение]:**

| Тип | Решение | Причина |
|---|---|---|
| Всё для игрока (осмотр, мастерская, сборка, здания) | один экран | общий мир, камера, выбранный объект; нет загрузок между шагами |
| Инструменты автора (Icon Studio, Track Studio) | отдельные сцены | пишут в `res://`, свои окна, не для игрока; запуск F6 как сейчас |
| Будущие тяжёлые редакторы (например профили рельса игрока) | отдельная сцена по необходимости | собственная геометрия и ввод |

### 22.5.2. Вход и выход

- **Первая версия (L1) [предложение]:** вход без роутера. `ModeController` запоминает предыдущий режим, открывает `LibraryScreen` оверлеем (`CanvasLayer`), ставит дерево на паузу (экран `process_mode = ALWAYS`), выключает 3D главного вьюпорта на время (`Viewport.disable_3d`, проверить в редакторе). При закрытии возвращает прежний режим и подсвечивает его кнопку.
- **После ATTN_19 F1:** вход через `SceneRouter.push('library')`. Экран делается по контракту `Screen` (`enter`, `exit`, `can_leave`), поэтому смена способа входа не меняет код экрана. Пауза Observe и правила паузы: [ATTN_19](ATTN_19_game_flow.md) §19.7.
- **Из главного меню (`menu`)**: `Model Studio` открывает тот же экран без макета (правила из профиля).
- Запуск отдельно для разработки: F6 на `library_screen.tscn`.

### 22.5.3. Вид сцены: варианты

**[=атн=] «Галерея со стеклянными полками или псевдоуправление от первого лица или оба варианта или нечто другое. Рабочий стол моделиста или чистый фон без имитации ... предложения».**

| Вариант | Что это | Плюсы | Минусы, стоимость |
|---|---|---|---|
| A. Чистая студия | нейтральный фон и студийный свет, как Icon Studio | уже есть код; лучшая читаемость модели; быстрый; годится для скриншотов и отладки | без «ощущения мастерской» |
| B. Стол моделиста | коврик, лампа, инструменты-декор, модель на столе | задаёт настроение Workshop; лампа даёт настоящий свет | немного декора из коробок и существующих материалов |
| C. Витрина со стеклянными полками | 3D-стеллаж, модели стоят по полкам | коллекционный азарт, «полка успехов» | стекло: дорогие отражения; взять упрощённый материал (прозрачность и Fresnel, без SSR); расстановка по коллекции |
| D. Витрина от первого лица | свободный обход стеллажа WASD и мышью | иммерсивность | нужны границы, высота камеры, коллизии; смысл есть только вместе с C |
| E. «Уголок моделиста» (нечто другое) | стеллаж над столом: модель с полки плавно «переезжает» на стол, камера сопровождает | единая композиция, B и C в одной сцене | стоит как B плюс C |

**Предложение:** общая оболочка с заменяемой сценой (`LibraryStage`: `clean`, `bench`, `shelf`). Идти по порядку: A (L1–L11), затем E как итоговый вид (L12), D только как необязательная опция E. Чистая студия остаётся навсегда как переключатель (скриншоты, слабые машины). Комнату Observe (`RoomBuilder`) не использовать: она привязана к `ObserveController`, а `fast_debug` сейчас её отключает (F9); фон Library строится из коробок. Look `workshop` ([ATTN_14](ATTN_14_observe_room.md)) подходит как стартовый для E.

**Паспорт отдельным ресурсом, не полем `EntitySetting` [предложение].** Не меняет существующие `.tres` и их `uid`; проверяется линтом. Поля появляются по шагам:

### 22.6.3. Связь с игрой

- **`VariantApplier.apply(instance, variant, info)`** применяет исполнение к экземпляру сцены: покраска (`surface_override_material` на **копии** базового материала, общий ресурс не меняется), детали (по ролям `PartRegistry`), свет (`LightConfig` копией), подстройка (копия `WagonConfig`). Работает одинаково в Library и в игре.
- **`C_Visual`** получает поле `variant` (Dictionary), применяет в `_on_instance_ready`, пишет в `save_data`. Старый сейв без поля грузится как раньше.
- **`EntityFactory.create_from_setting(setting, variant := {})`**: необязательный второй параметр, по умолчанию пусто (прежнее поведение).
- **Каталог Build:** категория «Мои исполнения» и «Мои здания» через провайдер каталога ([ATTN_17](ATTN_17_ui.md): `LibraryProvider`, шаблон `CatalogProvider`). Для Library коллекция берётся из `Global.object_dirs`.
- **Макет переносим:** исполнение и спецификация здания записываются в сейв макета **целиком**, а не ссылкой на файл `user://`; удаление файла исполнения макет не ломает.
- **Контур и подсветка** (`material_overlay`, `next_pass`) независимы от `surface_override_material`; проверка на совместимость в L4.

## 22.7. Модули: анализ и предложения

### 22.7.1. Collection: витрина, осмотр, справка

**Что:** каталог с поиском и фильтрами по фасетам (`CatalogMeta.FACET_SPECS`), паспорт модели, осмотр (орбита, Fit, шесть слотов ракурсов, автовращение), габариты из замера AABB в ю и в «метрах прототипа» (1 ю около 1 м, [ATTN_20](ATTN_20_track_studio.md) §20.2), состояние «закрыто или открыто».

**Справка по реальному прототипу:** данные из `ModelInfo.prototype` (дорога, серия, производитель, годы, роль) и короткая история. Контент пишет автор; пока паспорта нет, показываются имя, габариты и теги.

**Вид:** варианты A–E §22.5.3.

### 22.7.2. Customization: покраска, замена деталей, исполнения

Обширный раздел, делится на ступени (включаются правилами §22.4):

| Ступень | Что | Как | Ограничение |
|---|---|---|---|
| Цвет зон | покраска по зонам | зоны это поверхности меша (surface) или роли `PartRegistry`; `surface_override_material` на копии материала | у моделей с одной поверхностью только «весь корпус» (F3) |
| Отделка | матовая, глянец, металл | параметры `StandardMaterial3D`: шероховатость, металличность | колёса (шейдер `shader_wheel01_material`) не красятся |
| Декали | номера, надписи, полосы | узел `Decal` движка (Forward+), дочерний узел кузова, следует за вагоном | лимит кластерных элементов делится со светом: проверить в редакторе, бюджет ввести числом |
| Износ | потёртости, грязь | параметры шейдера-накладки (`material_overlay` занят контуром, нужен второй путь) | подтвердить способ в L3 |
| Детали | замена по ролям | опции `PartSlot` заменяют узел по роли | **нужна разметка моделей** (F3); без неё раздел пуст |
| Свет и механизмы | включение, цвет, добавление из пресетов | `LightConfig` и механизмы ([ATTN_16](ATTN_16_mechanisms.md)); уровень по `fit.level` | установка (уровень 2) только после ATTN_16 C1 и ATTN_10 D7; звук это слот-заглушка (TDD roadmap п. 6) |

**Главный риск:** монолитные модели (F3). Решение: покраска и осмотр работают на нынешних моделях, замена деталей включается по мере разметки моделей автором в Blender (`Custom Property` `role`, поддерживается `PartRegistry`).

### 22.7.3. Стенд: тестирование и подстройка подвижной и электрической части

- **Стенд «ролики»:** вагон закреплён, колёса крутятся от мотора, ползунок питания, переключатель направления, показания (`data/tools/speedometer_h.tscn`).
- **Электрика без `PGM` (F10).** Первая задача L6: проверить, можно ли получить тягу, ток и свет из `C_Engine` и `C_Mechanisms` без цепей `PGM`. Если нельзя, стенд подаёт виртуальное напряжение прямо в компонент. Испытательный путь с настоящим `PGM` откладывается до ATTN_10 D2–D3 и решения O2 ([ATTN_10](ATTN_10_dc_power_system.md) §10.6) **[открыто, Q13]**.
- **Подстройка (`test.level` 2):** поля `tuning` (масса, сцепление, сопротивление качению и т. п.) в пределах паспорта; значения идут в исполнение и применяются на копии `WagonConfig`. Пределы нужны, чтобы исполнение не ломало гибридную физику ([ATTN_TDD.md](ATTN_TDD.md) §8, §9).
- **«Проверить» (`test.level` 0):** одна кнопка и отчёт без цифр (свет, мотор, сцепки).

### 22.7.4. Реставрация

**Что:** игрок возвращает потрёпанную модель в хорошее состояние; это элемент заданий кампании и позднее связь с системой повреждений (GDD §10).

**Заготовка без системы повреждений:** износ, грязь и ржавчина это поля исполнения (`wear`, `dirt`, `rust`). Задание `RestorationTask`: исходное «ухудшенное» исполнение, цели (износ не выше порога, заменить детали, перекрасить) и инструменты: чистка (грязь), зачистка (ржавчина), покраска (L3), замена деталей (L5). Индикатор прогресса как у чистки в аналогах.

**Что нужно решить до L11:** нужен ли в игре компонент повреждений (`C_Damage`) и как вагон после схода попадает в Library (GDD §10). Это не входит в L11; L11 делает инструменты и задания на исполнениях. Не путать с Challenge «диагностика макета» (F14).

### 22.7.5. Сборка «из литников»: анализ идеи

**Идея:** здание приходит набором на литниках; игрок срезает детали, ставит их на основание и красит. Ритуал сборки из реального хобби; связь с открытием моделей и с «от готового к собранному» (GDD §2).

**Плюсы:** эмоциональный якорь режима («ритуал сборки», GDD §7); награда за кампанию; видимый результат; хорошо ложится на Tiny-Glade-подобную генерацию.

**Риски:** стоимость контента (каждая модель требует разделённых деталей и разметки шагов); утомительность (по отзывам о Model Builder); выбор мелких деталей мышью; монолитные модели (F3).

**Предложение [предложение]:**

- **Литники строятся автоматически из частей генератора зданий** (L7): стеновая панель, угловая стойка, скат крыши, окно, дверь, труба. Авторских литников нет: `SprueLayout` раскладывает части по рамкам, добавляет перемычки (runners) и литники (gates). Контент стоит столько же, сколько генератор. Поэтому генератор идёт раньше сборки (L7–L8, затем L9–L10).
- **Для вагонов и локомотивов литников нет**, пока модели монолитны (Q10). Возможная замена: «доводка» (зачистка швов, покраска, декали) без разборки.
- **Взаимодействие:** клик по части «срезает» её (анимация, след литника остаётся); перетаскивание на призрак с магнитом к сокету; неверная часть мягко возвращается; зачистка и клей необязательны. Без физики мелких деталей (движение твином).
- **Без наказания:** нет таймеров и ошибок; кнопки «Отменить шаг» и «Собрать само».
- **Режимы (`kit.mode`):** 0 пропуск (здание готово сразу), 1 срезать и поставить, 2 полный порядок с зачисткой и клеем.
- **Качество:** только косметика (видимость швов), без влияния на геймплей [открыто].

### 22.7.6. Генерация зданий (паттерн Tiny Glade): анализ идеи

**Идея:** здание строится из простых действий: контур на плите, высота этажей, крыша; окна и дверь расставляются правилами; «Другой вариант» меняет сид.

**Что берём из Tiny Glade:** бессеточный контур, правку тягой за грань, крышу как следствие контура, окна и двери как «контекстные» элементы по размеру стены, детерминированное оживление после структуры, отсутствие проигрыша.

**Что не берём в первой версии:** свободные кривые стены, рост плюща, повреждения штукатурки, взаимодействие соседних зданий.

**Предложение [предложение]:**

- `BuildingSpec` (данные): контур, число этажей, высота этажа, крыша (двускатная, плоская), стиль, сид, переопределения.
- **Контуры v1:** прямоугольник и L-образный из двух прямоугольников (крыша из прямоугольников без skeleton-алгоритма); произвольные многоугольники позже.
- **Правила окон и дверей:** по длине стены, высоте этажа, сиду; дверь на первом этаже у выбранной стены.
- **Геометрия** собирается кодом (`SurfaceTool`) в один `ArrayMesh` с поверхностями по материалам (до пяти), как `TrackMeshBuilder` собирает трак; материалы из PBR-наборов (сборщик `TrackMaterialBuilder`). Блендерных деталей не требуется.
- **Окна дают `GlowRect`** для ночного света ([ATTN_16](ATTN_16_mechanisms.md): сейчас у `house_01` они расставлены вручную): сгенерированное здание светится так же. Контракт `C_Mechanisms` принимает ли `LightConfig` из кода, проверить в L7.
- **Основание:** «юбка» вниз под фундамент; здания встают на землю, трак, поезд и слой гипса (`plaster`, [ATTN_13](ATTN_13_TerrainTools.md) §13.5), как нынешние.
- **Устройство в игре по канону EC** ([ATTN_TDD.md](ATTN_TDD.md) §2): компонент `C_BuildingGen` хранит `BuildingSpec` и строит меш; его сеттинг `buildinggen_setting.gd` по образцу `stylevisual_setting.gd`; данные идут в `save_data`.
- **Бюджет:** число вершин и треугольников эталонных зданий печатается тестом (как `track_style_bench`), порог задаётся по первому замеру.

## 22.9. План реализации (L0–L12)

Этапы объединены в группы для общей проверки в редакторе. Одна группа это один патч (коммит на свежий HEAD, применяется через `git am -3`, как в [ATTN_10](ATTN_10_dc_power_system.md) §10.9). Объём (S, M, L) это ориентир по числу файлов и кода, не по времени.

| Группа | Этапы | Что получает автор после проверки |
|---|---|---|
| A | L0, L1 | данные, правила, экран Library открывается из игры и закрывается, модель в кадре |
| B | L2 | коллекция, паспорт, осмотр |
| C | L3, L4 | покраска, исполнение живёт на макете и в сейве |
| D | L5, L6 | детали, свет, механизмы, стенд |
| E | L7, L8 | генератор зданий: ядро и интерфейс |
| F | L9, L10 | сборка из литников: данные и ритуал |
| G | L11 | реставрация (после решения по повреждениям) |
| H | L12 | витрина и «уголок моделиста» |

Зависимости от других разделов: L1 не требует ATTN_19 F1; уровень `fit.level` 2 требует ATTN_16 C1 и ATTN_10 D7; слот звука ждёт TDD roadmap п. 6; вход через роутер после ATTN_19 F1; вливание `LibraryRules` в общие правила после ATTN_10 D7. Порядок L7 до L9 сознательный: части литников строит генератор (§22.7.5).

Общая проверка для всех групп: запуск F5 игры без Library ведёт себя как раньше; в Output нет новых ошибок и предупреждений; старые сейвы (`res://saves/savegame.tres`, `autosave.tres`) загружаются.

## 22.10. Риски

| № | Риск | Влияние | Как закрываем |
|---|---|---|---|
| R1 | Монолитные модели (F3): детали и литники на нынешних моделях невозможны | замена деталей и сборка вагонов недоступны | покраска по surface; разметка моделей автором; литники только у зданий |
| R2 | `PGM` глобален (F10) | стенд может испортить цепи макета | виртуальное питание на стенде; решение Q13 |
| R3 | Декали (`Decal`) и стекло делят лимит кластерных элементов со светом | просадка fps, пропажа света | бюджет декалей числом, замер в L12 и L3, упрощённое стекло |
| R4 | `surface_override_material` и служебные слои (`material_overlay`, `next_pass`) | контур или подсветка не видны | проверка в L4; износ идёт вторым путём (L3) |
| R5 | Версионирование JSON | старая игра стирает данные новой | поле `v`, неизвестные поля сохраняются |
| R6 | Стоимость контента (паспорта, разметка, стили зданий) | режим пустой | паспорта необязательны; генератор вместо авторских зданий |
| R7 | Режим большой | долго нет результата | группы A–D дают рабочую мастерскую без генератора и литников |
| R8 | `fast_debug` зашит (F9) | Observe и комната выключены, документы расходятся | Library не зависит от них; автору решить про чтение `--fast` |
| R9 | Два мира рендерятся одновременно при оверлее | просадка fps | `disable_3d` главного вьюпорта на время; замер в L1 |
| R10 | Запись в `res://` работает только из редактора | сборка игрока не сохранит | все данные игрока в `user://` |
| R11 | Старые сейвы без поля исполнения | поломка загрузки | поле необязательное; проверка в каждой группе |
| R12 | Дубль списка папок каталога (F11) | коллекция и lint расходятся | один вызов `EntityCatalogProvider.list_resources` |
