# TDD — Simulator of Tabletop Railway

## 1. Purpose
Этот документ описывает техническую архитектуру и реализацию систем игры.

Геймплей и дизайн задач находятся в [GDD.md](GDD.md).

## 2. Architecture
Проект построен на архитектуре Entity-Component (EC), ориентированной на узлы (Nodes) в Godot v4.8. Отличительная черта системы — максимальная автономность компонентов через внутреннюю шину событий (Event Bus).

- **Отказ от Systems.** Вся логика поведения инкапсулирована внутри самих компонентов.
- **Маршрутизация через события.** Инструменты (Tools) не ищут конкретные компоненты (`get_comp(C_Draggable)`). Они полностью "слепы" и работают как передатчики ввода: тул транслирует приказ в сущность через `send_event`.
- **Реактивность.** Компонент сам решает, как реагировать на событие. Добавление нового компонента автоматически наделяет объект новым поведением без переписывания контроллеров.
- **Важная ремарка.** Системные сервисы (синглтоны) могут напрямую взаимодействовать с компонентами при предварительной проверке их существования, и наоборот. Например, `PowerGridManager` (PGM) напрямую оперирует с `C_Power_Clip`.

## 3. Структура ядра (Core)

- **`Entity` (`class_name Entity extends Node3D`)** — логический контейнер и локальный Event Bus. Управляет жизненным циклом компонентов. При вызове `send_event(event_name, data)` транслирует событие всем дочерним компонентам.
- **`Component` (`class_name Component extends Node`)** — базовый класс для всех компонентов. Живёт в дереве как дочерний узел Entity и слушает её события. При `queue_free()` Godot безопасно отключает все связи.
- **`EntityFactory` & `Settings`** — фабрика собирает Entity на основе ресурса-шаблона (`EntitySetting`), содержащего список чертежей компонентов (`ComponentSettings`).

## 4. Классификация компонентов

Три жёстко разделённых типа:

### 4.1 Capabilities (Способности / "умные" компоненты)
Определяют, что объект умеет делать. Присутствуют на объекте всегда. Содержат логику и слушают события сущности.
- `C_Draggable` — не ждёт вызова, реагирует на абстрактный приказ `on_drag_moved`.
- `C_Blockable` — сенсор коллизий; подключается ко всем `Area3D` сущности, считает `overlaps` и вешает/снимает метку `C_Blocked`.

### 4.2 States (Состояния / "глупые" метки)
Временные флаги, вешаемые инструментами. Не имеют свойств (например, у `C_Blocked` нет `is_blocked`). При добавлении/удалении могут рассылать события (например, требование сменить цвет).

### 4.3 Visual / Data (абстрактный рендерер)
`C_Visual` — полностью "тупой рендерер". Не проверяет компоненты по именам (`if has_comp(C_Ghost)`). Рисует только то, что ему приказали другие компоненты через события с наивысшим приоритетом.


## 5. Build. Паттерн инструментов (Tools)

`ToolController` — дирижёр, переключает активные инструменты режима BUILD. Инструменты ничего не вычисляют для объектов — только маршрутизируют данные.

- **`BuildTool`** — спавн призрака (`ghost`); отправляет события инициализации и перемещения.
- **`SelectTool`** — ховер, клик (Select), инициация драга существующих объектов; работает с конкретными событиями мыши.
- **`DragTool`** — перемещение объекта; посылает `on_drag_moved` в `target_entity`; при отмене возвращает объект на `initial_transform`.

## 6. Физика, слои и коллизии

Вместо `StaticBody3D` для детекции блокировок используются `Area3D` для точной реакции на пересечения.

**Маски и слои:**
- Слой 1 — Земля (Ground)
- Слой 3 — Траки (рабочие объекты)
- Слой 4 — Сокет(трак)
- Слой 5 — Вагоны (рабочие объекты)
- Слой 11 — Ghost (рейкасты инструментов игнорируют этот слой)
- Слой 11 — Selected/Drag (коллизии выбранного объекта переносятся сюда)


## 7. Технические решения и анти-паттерны

- **Entity как контейнер.** `Entity` (наследник `Node3D`) допускает дочерние ноды-некомпоненты, но не должен манипулировать ими напрямую. Эти ноды контролируются компонентами, которые их создали; доступ из других компонентов — только через шину событий.
  - `Path3D` — путь/кривая трака. По ней генерируются коллизии трака(балласт и рельсы) Хозяин: `C_Path`.
  - `Area3D` — сокеты трака для коннектов с другими траками. Хозяин: `C_Socket`.
  - `Node3D` — основная нода ентити. Хозяин: `C_Visual`
  - `RigidBody3D` — основная нода ентити вагона. Хозяин: `C_TrainVisual`
- **Node Ownership Principle.** Принцип Владения Нодами:
Entity является лишь пустым логическим контейнером и шиной событий (`Event Bus`). Все дочерние функциональные и визуальные ноды (MeshInstance, RayCast, Area3D, Path3D) должны инстанцироваться и управляться исключительно тем компонентом, к зоне ответственности которого они относятся.  
  - *`C_Path`* — владеет `Path3D` и коллизиями балласта.  
  - *`C_Socket`* — владеет `Area3D` для точек стыковки.  
  - *`C_TrainVisual` / `C_Chassis`* — владеют мешами кузова, тележками (`Node3D`), колесными парами и сенсорами (`RayCast3D`).  

  *Запрещается*: Прямое обращение одного компонента к нодам другого компонента (например, `get_node("BogieMesh")`). Взаимодействие происходит только через чтение переменных компонента или отправку событий.

- **Угроза пересборки физики (Infinite Rebuild Loop).** Переназначение `collision_layer` вызывает сброс физических пересечений. Слои меняются только если новое значение отличается от текущего.
- **Визуальный водопад (Event-Driven C_Visual).** `C_Visual` не содержит жёстких проверок (`has_comp`). Компоненты сами отправляют событие `set_visual_state` с материалом и приоритетом. `C_Visual` применяет материал с наивысшим приоритетом.
- **Дроп заблокированного объекта.** При отмене `DragTool` возвращает объект на исходную позицию и вручную удаляет метку `C_Blocked`, но никогда не удаляет способность `C_Blockable`.
- **Магнитный снаппинг (`C_Socket`).** Компонент для логических точек стыковки и хелпер для подмены координат `target_pos` рейкаста при перетаскивании.
- **Pivot вместо AABB.** Для выравнивания объектов используются компоненты-пивоты моделей или `drag_offset`.
- **InfoPanel.** Панель отображения информации об объекте; видна при селекте. Заголовок — имя объекта. Закладки: основная (описание, длина, радиус…), электрика, позиция и поворот, внешний вид, дебаг (компоненты, соседи и т.д.). Закладки включаются динамически в зависимости от наличия компонентов/категории объекта (в процессе реализации).


## 8. Railway concept — техническая организация

### 8.1 Wagon - базовая сущность поезда

Включает набор компонентов, общих для всех дочерних сущностей. Может тащиться сцепкой, толкаться другим вагоном, получать "пинок" от игрока; перемещается перетаскиванием мышью.
Характеристики: 
- масса;
- коэффициент трения подшипников (длина свободного хода);
- горизонтальные/вертикальные допуски хода (пружины, амортизаторы);

Элементы вагона отличаются по количеству и свойствам. В минимальном составе содержит кузов и боги.

**Кузов.** Базовый элемент. Включает физику `RigidBody3D`при сходе.

**Bogie.** Тележка, на которую установлен кузов. Как правило, вагон крепится на передний и задний боги, которые могут вращаться вокруг точки крепления (люфты и YAW вращение). 

**Wheel pair.** Левое и правое колёса жёстко соединены, образуют колёсную пару. Колёсные пары устанавливаются на боги. Не управляются физикой. Вращение определяет математика. Коллизии колесной пары - это коллизии боги. Могут быть в 2х вариантах: 1 бокс на всю боги, 2 бокса(левая и правая лыжи), которые имитируют контакт с поверхностью в физикс режиме. 

**Coupler.** Сцепка для соединения вагонов

**Engine.** Мотор принимает энергию от трака и двигает вагон.

### 8.2. Loco. Вагон с мотором. 

Двигается самостоятельно на рельсах с подведённым электричеством. 
Характеристики (дополнительно к Wagon): 
- мощность;
- начальное напряжение для старта движения;
- блокировка колёс при отключении питания.

### 8.3 Движение\ Hybrid Physics.

Если вагон на рельсах, то движется по сплайну трака, отвечает `C_Chassis`.  За поведение вне рельсов отвечает физический движок Godot через `C_Kinematics`.

#### 8.3.1. Traction & Contact (Локомоция и контакт с путем)
*Отвечает за передачу энергии в движение и базовые сопротивления.*

- [ ] **Wheel adhesion (Сцепление):** Ограничение максимальной тяги до срыва в скольжение. Зависит от веса и погоды (снег, дождь).   
- [x] **Wheel slip (Пробуксовка):** Физическая потеря тяги при превышении лимита сцепления.
- [x] **Wheel visual slip:** Визуальное вращение колес быстрее скорости движения шасси.
- [x] **Rolling resistance:** Базовое сопротивление качению (трение подшипников), определяющее длину свободного хода.   
- [ ] **Grade resistance (Градиентное сопротивление):** Влияние уклонов (подъемы и спуски) на ускорение и торможение.   
- [ ] **Curve resistance (Сопротивление в кривых):** Дополнительное трение при прохождении кривых участков пути (включая Flange contact — трение реборды колеса).

---

#### 8.3.2. Body Dynamics & Suspension (Динамика кузова и подвески)
*Визуально-физические "ассисты", создающие ощущение массы и работы рессор с учетом HO-масштаба.*

- [x] **Vertical suspension (Вертикальная подвеска):** Подпрыгивание кузова; пустой вагон прыгает жестче, груженый — плавнее.
- [x] **Body roll (Поперечный крен):** Наклон кузова вбок от центробежной силы или неровностей.
- [x] **Pitch (Продольный крен / Кивок):** Перенос веса (визуальный tilt меша) при резком ускорении или торможении.
- [x] **Lateral suspension (Боковая раскачка):** Шатание на рессорах при движении по прямой или на стыках.
- [x] **Bogie yaw:** Поворот тележек (боги) по касательной к сплайну.   

---

#### 8.3.3. Track Interaction (Взаимодействие с неровностями)
*Как несовершенство железнодорожного полотна влияет на вагон.*

- [ ] **Track irregularity (Мелкая тряска):** Случайный высокочастотный шум подвески от неровностей пути и грязи.   
- [x] **Rail joints (Стыки):** Периодические удары (вибрация и звук), зависящие от пройденной дистанции, а не от времени.   
- [ ] **Switch jolts (Удары на стрелках):** Резкие боковые и вертикальные толчки при прохождении тележкой узлов разветвления.   

---

#### 8.3.4. Train Physics (Физика состава)
*Взаимодействие вагонов между собой после реализации системы сцепок.*

- [x] **Coupler slack (Люфт сцепки):** Свободный ход (зазоры) между вагонами. Характерный рывок и "лязг" по цепочке при старте локомотива.   
- [x] **Coupler damping (Амортизация сцепки):** Смягчение ударов при сжатии/растяжении состава (пружинный буфер).
- [x] **Push/Pull dynamics (Динамика толкания/тяги):** Передача тяги или инерции от соседнего вагона через компонент `C_Coupler`.   

---

#### 8.3.5. Derailment Mechanics (Условия схода с рельс)
*Триггеры для отключения сплайн-ассиста и перехода в `C_Kinematics`.*

- [x] **Centrifugal derail (Центробежный сход):** Превышение лимита сцепления реборды в повороте.   
- [x] **Track End (Тупик):** Сход из-за отсутствия пути.   
- [x] **Tight Curve (Излом):** Сход из-за непроходимого радиуса.   
- [ ] **Dynamic derail (Сход от раскачки):** Критический резонанс систем Body roll, Hunting или Track irregularity (планируется).

## 9. Масштабирование вертикальной динамики железнодорожных моделей. 
При определении масштаба единиц Годот и реальных размеров исходим из соображений: рекомендуемые величины движка и маленькие размеры прототипов.
- 1 см реальной модели соответствует 1 м в единицах Godot (0,01м -> 1м);
- линейный масштаб относительно физического прототипа составляет 1:100;
- масса объектов также задаётся в представлении 1:10(для подтягивания к рекомендуемым величинам движка);
	например, вагон массой 0,13 кг в реальной HO-модели имеет массу 1.3 кг в физическом мире Godot;
- стандартная гравитация Godot составляет 9,81 м/с².

## 9.1 Проблема масштабирования

Такое масштабирование позволяет использовать размеры объектов, удобные для физического движка, однако приводит к различию между пространственным масштабом и временной динамикой движения.

Пример, типовой вагон:
```
- размеры в юнитах Godot: `10 × 2 × 3,4 м`;
- масса: `1,3 кг`;
- эквивалентная реальная модель HO: масса около `0,13 кг`, длина около `0,10 м`.
```

При стандартной гравитации `9,81 м/с²` падение физической модели и падение реального вагона не сохраняют одинаковое время процесса.
Геометрия объекта увеличена в 100 раз, а характерное время падения увеличивается в 10 раз.

С точки зрения пользователя это воспринимается как замедленное, чрезмерно «тяжёлое» или инертное поведение модели при отрыве от рельсов и падении.


## 9.2 Требуемое поведение

Необходимо реализовать специальный физический ассист, корректирующий вертикальную динамику вагонов и других железнодорожных объектов.

Цель ассиста:

> Сохранить для вертикальных движений временной масштаб реальной HO-модели, несмотря на увеличение геометрии объекта в 100 раз.

Для данного режима требуется:

- сохранять пространственный масштаб `S = 100`;
- не изменять визуальные размеры объектов;
- не изменять задаваемую массу объектов;
- сохранять стандартную гравитацию проекта для остальных физических объектов;
- для железнодорожных объектов использовать эффективное вертикальное ускорение. 

## 9.3 Формула ассиста

Базовый коэффициент эффективной гравитации определяется как:

Расчет падения реальной модели на 0,2 м
T = sqrt( (2 * 0,2) / 9,81) 
v = 0,2м / 0,2с = 1 м/с

Базовая контрольная точка:

Время ~0,2с и средняя скорость ~1 м/с. 

Базовая контрольная точка:

```text
HO-модель:
0,2 м падения
≈ 0,2 с

Физическая модель:
20 м падения
≈ 0,2 с 
```
Именно это поведение является целевым для вертикальной динамики.

## 10. Power System — техническая реализация

Опираемся на системы **HO** макетов ж/д. Два режима питания: **DC** (Direct Current, аналоговое) и **DCC** (Digital Command Control, цифровое).

### 10.1 DC Controller с логикой PWM
Начальное состояние питания — DC, приоритетное внедрение. Управление сетью ВС осуществляет системный сервис `PowerGridManager(PGM)`

**PWM (ШИМ — широтно-импульсная модуляция)** используется для раздельного управления цепями железной дороги с аналоговой архитектурой.

**`DCController`** — базовый контроллер питания. Выдаёт значения `-100 ... +100`, из которых получается нужный диапазон напряжений. Есть кнопка аварийного отключения. Переключатель цепей: напряжение в цепи сохраняется при переключении контроллера на другую цепь, либо возможно управление всеми цепями одновременно (главное преимущество PWM-структуры). Управление — ручкой или слайдером в зависимости от модели контроллера. Базовая модель может всё, производные модели — варианты с заблокированными функциями.

Игрок в перспективе может начать с простейшего DC и развить дорогу до продвинутого PWM-варианта.

### 10.2 PowerClip
Соединяет Controller с track, определяет подключение и полярность. Термин сохранён как у **PIKO** .

Если игрок ставит клип на трак (или трак с клипом), всё подключённое к этому траку получает напряжение с контроллера. Начало/конец трака определяются `Path3D`, которая есть у каждого трака.

Визуально на траке клип отображается специальной нодой/мешем (коробочка) с номером контура и текущим напряжением.

### 10.3 Contours
Группа соединённых track, образующая электрический контур. Каждый контур имеет свой клип и не соединяется с другими контурами (исключение — стрелки и спецтраки). 

### 10.4 Power Layer
Визуализирует:
- питание;
- полярность;
- контуры;
- PowerClip;
- напряжение.

### 10.5 Track power
Определяет возможность передачи напряжения с контроллера на Локо. Управляет `C_PowerTrack`и подключен к сети через id контура.

### 10.6 Loco power
Локо управляется `C_Engine`(Мотор). Движется в соответствии с напряжением, поданным на контакторы (колёса) от контроллера напряжения через трак.

### 10.7 DCC (Digital Command Control)
Цифровая система управления. Конкретный протокол и архитектура находятся в разработке.

Entity не управляет внутренним поведением этих nodes напрямую.

## 12. Info Panel

# 14. Observe: атмосфера, свет и комната
Observe это созерцательная награда за Build/Operate: игрок смотрит на живой макет, меняет свет, ракурс, делает скриншот.

## 14.0. Концепт и границы

**Объект первого прохода: комната ребёнка 10 лет, в которой стоит стол с макетом.** Главный принцип: стол и поезда получают весь бюджет, комната работает как декорация (диорама в диораме).

**Референсы (что именно берём):**
- *LEGO Horizon Adventures*: миниатюрная картинка. Насыщенная палитра, мягкие тени, фаски на всех гранях, пластиковый блик, неглубокая резкость.
- *House of Golf 2*: комната как сцена. Крупные простые формы, чистые цвета, 6–10 узнаваемых предметов, мелочи только у центра внимания.

**Вне объёма этого раздела:** настройки отдельных параметров графики в игре (позже, §14.11), Library (рассматривание моделей), погода как физика, Decor/Room как расстановка игроком.

### Перспективный технический roadmap

1. [x] **Flex Tracks (гибкие рельсы).** Сборка сущности с `C_Curve` (математика точек), `C_Visual_Flex` (генерация меша через PathMesh3D), `C_Handle` (управление изгибом).
2. [x] **Slope Track (наклон трака).** Механизм подъёма/опускания одного конца трака без изменения позиции второго конца.
3. [ ] **Selectable Control Ground.** Механизм контроля вертикального положения и угла наклона трака при перетаскивании по неровным поверхностям — альтернатива/дополнение к текущему методу контроля центра трака. Известная проблема: при вращении трака вокруг оси X (pitch) один конец уходит под землю — требует исправления.
4. [x] **Train.** Сцепка вагонов.
5. [x] **Reality Simulation.** Реалистичное поведение поезда при движении: стыки, неровности, покачивание, сходы с рельсов.

7. [ ] **Decor collection.** Предметы окружения.
8. [ ] **Room.** Помещения для размещения макета.
9. [ ] **Customization.** Покраска, замена элементов, варианты исполнения.
10. [ ] **Graphic setting.** Выбор стилистики визуала.
11. [ ] **Switch (turnout), Crossing, Buffer Stop, Track.** Развитие траков.
12. [ ] **Electric connections.** Продвинутое управление питанием: слой управления, разводка проводов от контроллера к клипу, переключение полярности, разветвители, управление элементами (свет в домиках, шлагбаумы и т.д.).

14. [ ] **Car System.** Автомобильное и водное движение по макету.
